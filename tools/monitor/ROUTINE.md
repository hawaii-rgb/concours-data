# Concours 일일 대회 모니터링 루틴 (Claude 클라우드 예약용)

이 문서는 **매일 1회 실행되는 Claude 클라우드 예약 루틴(`/schedule`)의 태스크 프롬프트**다.
아래 "루틴 지시" 전체를 예약 태스크로 등록한다. 목적: 신규·회차전환·일정변경 대회를
감지해 **사용자 승인 없이 곧바로** `concours-data`에 push → 앱 아이콘 배지로 사용자에게 알림.

---

## 배경 (에이전트가 알아야 할 것)

- **데이터 리포**: `github.com/hawaii-rgb/concours-data` — 앱이 실시간 fetch하는 라이브 소스.
  - 파일: `competitions.json`(대회당 항목 1개, 최신 회차만) + `images/<slug>/pNN.png`(포스터).
  - 앱은 `officialName|round|month`를 id로 씀 → **회차·월이 바뀌면 새 id로 인식 → 앱 배지 자동 점등.**
- **스크립트**: 이 저장소 `tools/monitor/`
  - `targets.py` — 오늘의 감시 타깃 생성(연중개최예상 기반).
  - `safe_merge.py` — 변경 반영 가드레일(이것으로만 JSON을 수정한다).
- **오늘 날짜**는 루틴 실행 환경의 실제 시스템 날짜를 쓴다.

## ⛔ 절대 규칙 (안전·저작권)

1. **`competitions.json` 편집은 `safe_merge.py`로만.** 직접 손으로 JSON을 고치지 않는다.
2. **사실 필드만.** 날짜·장소·부문·접수·회차·지역·주최. (safe_merge가 그 외를 무시함)
3. **`images/` 디렉토리는 절대 건드리지 않는다.** competitions.json만 커밋. (과거 `git add -A`가
   이미지 대량 삭제를 원격에 전파한 사고가 있었음 — `git add competitions.json`만 스테이징.)
4. **포스터는 지자체 공홈 원본만.** 국악신문·국악타임즈의 **워터마크 이미지/요강 원문은 재사용 금지**
   (저작권). 이 3소스는 "대회가 떴다"는 **발견 + 사실정보 추출**용으로만 쓴다. 포스터를 못 구하면
   `noticeImages`는 빈 채로 두고 `sourceUrl`에 공홈/공고 링크만 넣는다.
5. **삭제 금지.** 신규 추가 / 기존 항목의 사실 필드 갱신만. 대회를 지우지 않는다.
6. 확신이 낮은 항목은 **넣지 않는다.** 잘못된 정보가 바로 실사용자 앱에 노출되므로 보수적으로.
   (사용자는 오류를 대개 못 잡아낸다 → **애초에 안 틀리는 게 목표.** 빠뜨리면 다음날 재시도되지만,
   틀리면 실사용자에게 바로 노출된다. 의심스러우면 반영 대신 스킵.)
7. ⛔ **하드파싱 금지.** 소스 HTML을 정규식·CSS셀렉터로 긁지 않는다. **클로드가 실제 게시글·요강·
   포스터를 풀 추론으로 읽고 사실을 추출한다** — 이미지 요강은 비전으로 OCR·판독. 사이트 구조가
   바뀌어도 견고해야 하고, 정규식 추출의 오탐(엉뚱한 회차·연도·다른 대회 혼입)을 원천 차단한다.
   (단, `targets.py`·`safe_merge.py`는 우리 competitions.json만 다루는 결정적 안전 스크립트이므로 계속 사용.)
8. ★ **검증 없이 쓰지 않는다.** 아래 "신뢰성 검증 게이트"를 **모두 통과한 사실만** changes.json에 넣는다.

## ⛔ 필드 품질 규칙 (2026-07 실사고 반영 — 반드시 준수)

앱이 필드 변경을 사용자에게 **수정 리본·팝업**으로 보여주므로, 아래를 어기면 실사용자에게 오류/노이즈가 바로 노출된다.

### (A) 연락처(`details.contact`) 규칙 — 전화 중심, 접수용 이메일 금지
실사고: 보강이 **서류접수용 이메일을 연락처에 넣어 전화번호를 삭제**함(송파·영등포). 앞으로:
- **연락처 = 전화번호(+팩스) 중심.** **서류접수용 이메일은 연락처에 넣지 않는다** — 접수 정보는 `applyText`
  (그리고 있으면 `recipientEmail`)에 둔다.
- 연락처에 이메일은 **접수용과 명백히 다른 '문의용' 이메일이 따로 있을 때만** 추가한다.
  (판별: 요강의 "문의/연락처" 블록에 있는 이메일 = 문의용 / "접수방법·제출처"의 이메일 = 접수용.)
- **기존 전화·팩스를 지우거나 개수를 줄이지 않는다.** 보강은 **덮어쓰기보다 추가·보존**을 우선.

### (B) 불필요한 재작성 금지 — 데이터 안정성(가짜 '수정' 방지)
실사고: 장소를 `팔공홀, 비슬홀`→`팔공홀·비슬홀`(구두점만), 일정을 같은 날짜 다른 문구로 다시 써서
**가짜 '수정' 알림**을 만듦(대구국악제). 앞으로:
- 기존 필드를 **구두점·공백·표현만 다른 값으로 덮어쓰지 않는다.** 사실이 같으면 **그대로 둔다.**
- `update`에는 **의미 있는 변경**(접수마감·개최일·장소·회차·부문·접수기간의 실제 변화)만 넣는다.
- 판단 기준: 공백·구두점을 제거해 비교했을 때 같으면 = 변경 아님 → changes.json에서 제외.

### (C) 중복/이중등록 금지 — 앱 '핑퐁' 사고 방지 (2026-07 실사고 반영)
실사고: 임실전국국악경연대회 2026 제9회를 반영하며 **같은 대회를 두 항목으로 이중등록**함 —
① 새 '국창…제9회'를 `new`로 추가하고, ② 동시에 옛 '제5회 임실'(plain, 접두어 생략형)을 `update`로
제9회로 바꿔버림. 두 항목의 id(`이름|회차|월`)가 같아져 앱 스냅샷 슬롯을 공유 → **접수중↔예정
무한 NEW 핑퐁**(모든 기기). 원인: plain 이름("임실전국국악경연대회")과 접두어형("국창 전도성·이화중선
추모 임실전국국악경연대회")이 **정규화 base가 달라 서로 다른 대회로 오인**됨. 앞으로:
- **한 공고 = 한 항목.** 한 대회의 새 회차는 **기존 항목을 제자리 `update`**로 올린다 —
  같은 시리즈를 `new`로 또 만들지 않는다. `new`는 **정말로 데이터셋에 없던 대회**일 때만.
- **같은 시리즈 판별 시 접두어/생략형을 함께 본다.** 추모·수식 접두어(국창 ○○ 추모 등)만 다른
  이름은 **같은 대회**일 수 있다 — base가 다르다고 새 대회로 단정하지 말고, 지역·주최·개최지로 교차확인.
- **회차 점프(>1) 경고.** `update`가 회차를 N→N+1이 아니라 크게 건너뛰면(예: 제5회→제9회) **엉뚱한
  항목을 지목**한 신호 → 스킵·재검토.
- 이미 데이터에 **같은 대회가 두 항목으로 갈려 있으면**(plain + 접두어형 등) 그 사실을 로그하고,
  하나로 병합하는 정정은 **대화형 세션(관리자 승인)**에서 처리 — 자동 루틴이 임의 삭제하지 않는다.
- ★ **표기 변형을 정리했으면 `aka`에 영구 기록** (재판단·재중복 방지 — 무상태 루틴의 핵심 보완):
  동일 대회의 표기 변형(한자/한글, 접두어 유무 등)을 하나로 정리(삭제·병합)했다면, **남긴 canonical
  항목의 `aka` 배열에 그 변형 이름**을 넣는다. 예: `대전전국국악경연대회` 항목에 `"aka": ["大田전국국악경연대회"]`.
  `targets.py`·`safe_merge.py`가 **aka를 all_keys·매칭에 포함**하므로, 내년에 그 변형이 재등장해도 **신규가
  아닌 기존으로 잡혀 업데이트**된다(매년 다시 판단하지 않음). ※ 정체성만 고정 — 필드 값(날짜·장소)은 매년 재추출.
- ★ `safe_merge.py`가 **하드 차단하는 것**(반영 자체를 막음): ① 동일 id 중복(핑퐁) → 쓰기·커밋 중단(exit 2)
  ② 결과 id가 다른 항목과 충돌하는 `update` → 스킵 ③ 같은 sourceUrl+회차 신규(동일대회 이중등록) → 스킵
  ④ **날짜 순서 오류**(접수시작>마감, 마감>대회일 등) 신규/갱신 → 스킵. **경고(로그만)**: 같은 sourceUrl+회차
  기존 중복 / **요일 정합성 불일치**(요강 명시 요일 vs 실제 = 연도 오류 신호) / month↔대회일 월 불일치.
  → 런 로그의 ⚠경고는 **오류 후보**이니 확인해 정정한다(특히 요일불일치=연도 의심).

## 감지 소스 3개 — **신뢰할 수 있는 사실 소스**

국악신문·국악타임즈·콘테스트코리아는 **신뢰한다.** 여기서 확인된 신규·회차전환·일정 정보를
**사실로 반영할 수 있다** — 공홈이 없거나 안 열려도(503 등) 무방하다. 공홈은 있으면 교차확인·보강용
이지 필수는 아니다. 클로드가 각 사이트를 **열어 읽고**(리스트·검색·최근 공고) 국악 경연대회를 후보로
뽑는다 — 정규식 스크래핑 금지, 네가 직접 판독. (콘테스트코리아는 회차 반영이 지연될 수 있으니 회차
숫자는 게시글 원문으로 확인.)

### ★★ 목록 훑기 + 검색을 **반드시 병행** (구조적 사각지대 차단)

**섹션 목록만 훑으면 영구히 못 잡는 대회가 실재한다.** 2026-07 전수감사 실측:
국악타임즈 "2026 제1회 대한민국 풀피리 경연대회"(기사 82798)는 제목에 `[경연대회]`를 달고도
**경연대회 섹션(`sec_no=65`)에 편성되지 않아** 섹션 목록·전체기사 목록 어디에도 뜨지 않았다
(섹션 최신글이 82724인데 그보다 뒤에 나온 82798이 목록에 없음 = 편집자의 섹션 지정 누락).
**검색(`search=경연대회`)으로만 최상위에 잡혔다.** 실제로 이 대회는 루틴이 하루 잡았다가
다음 실행에서 놓쳤다 — "며칠 지나도 재발견 안 됨"은 확률이 아니라 **구조적 사각지대**다.
→ **매 실행마다 소스별로 (1) 섹션/카테고리 목록 + (2) 키워드 검색을 둘 다 수행한다.**
   (역으로 목록이 검색보다 더 잡는 경우도 실측됨 — 국악신문에서 목록이 검색 누락분 14건 추가 발견.)

### 소스별 실측 구조 (2026-07 확인. 다르면 구조가 바뀐 것이니 홈을 열어 실제 href를 읽고 확인)

- **콘테스트코리아** `contestkorea.com`
  - 목록: `/sub/list.php?int_gbn=1&displayrow=30&Txt_bcode=030910001` (음악·콩쿠르·댄스), `&page=N`
  - 상세: `/sub/view.php?int_gbn=1&Txt_bcode=030910001&str_no=<번호>`
  - 검색 키워드: 국악·전국국악·판소리·민요·경창·가야금·무용경연·기악·전통예술·농악·병창·거문고·정가·아리랑
  - 회차 반영이 지연될 수 있으니 **회차 숫자는 게시글 원문으로 확인.**
- **국악신문** `kukak21.com` — **그누보드.** (⛔ `article.html?no=` 는 국악타임즈 형식이며 여기선 404)
  - 기사: `/bbs/board.php?bo_table=news&wr_id=<번호>`
  - 섹션 목록: `/bbs/board.php?bo_table=news&me_id=<N>&me_code=<숫자코드>` (섹션 87개), 전체: `/bbs/all.php`
  - **검색: `/bbs/search.php?sfl=wr_subject&sop=and&stx=<URL인코딩 키워드>`** (본문까지: `sfl=wr_subject||wr_content`)
    ⛔ `board.php?bo_table=news&sfl=..&stx=..` 조합은 **에러 없이 조용히 0건**을 반환한다. 반드시 `search.php`.
  - ⚠ 전 페이지에 **공고 사이드바 위젯**이 붙어 있어 무의미 질의에도 대회 제목·`wr_id`가 60여 개 깔린다.
    - **wr_id 개수만 세면 "결과 있음"으로 착각한다.** 실측 기준선: 무의미 질의(`zzzznonsense`)에도 wr_id 약 64개.
    - 판정법: 결과 파싱은 **`<div class="article-list">` 블록 내부로 한정**하고, 질의어가 제목에 실제로
      들어있는지 확인하라. (실측: `풀피리` 질의 시 board.php=본문 출현 0회(0건), search.php=11회(정상))
- **국악타임즈** `gugaktimes.com`
  - 기사: `/news/article.html?no=<번호>`
  - 섹션 목록: `/news/section_list_all.html?sec_no=65` (경연대회), `&page=N`
  - **검색: `/news/search_result.html?search=<키워드>`** ← 파라미터는 `search`. (`sc_word`·`stx`·`keyword`는 전부 0건)
    전기간은 `&all=1` (검색 기본값이 "최근 3년"이라 과거분이 잘림)
  - ⚠ 검색 결과에 트로트 방송 기사 등 무관 건이 섞인다 → 클로드가 제목·본문을 읽고 판정.

→ 후보를 찾으면 아래 **검증 게이트**로 (날짜·회차의) 정합성을 확인한 뒤 반영한다.

## 공홈·확장 소스 검색 (★ 배포 전 풀 목록 완성을 위해 '보강' → '필수'로 격상)

목표: 배포 전까지 풀 목록을 **완성**한다. 3소스만으로는 부족하다 — 대회마다 공식 정보가
3소스가 아닌 **자체 공홈·기관 홈·네이버 개방카페·인스타그램**에만 있는 경우가 있다
(실측: 정읍사 제36회 = 콘테코엔 제35회까지뿐, 제36회 요강·포스터는 **네이버 공식카페에만** 있었음).

### (1) 대회별 공홈까지 추적 — 클라우드 가능
- 각 `targets[]` 대회와 신규 후보에 대해 3소스 외 **주최측 공식 공고**를 찾는다:
  - 기존 항목의 `sourceUrl`이 공홈/카페면 **그걸 직접 페치해 최신 상태 재확인**(접수마감 변경 등).
  - 3소스 기사에 링크된 주최기관 홈(go.kr/or.kr/문화재단 등) URL을 페치해 사실 보강.
  - 특히 **`confidence: partial` 이거나 `details.applyStart`/`applyEnd` 중 하나라도 빈 기존 항목은
    우선 보강 대상** — 공홈/카페/첨부 요강에서 접수시작·접수마감·부문·참가비를 채운다. (풀 목록 "완성"의 핵심.)
- go.kr/or.kr 등 관공서·기관 홈은 클라우드에서 대체로 열린다.

### (2) 네이버 개방카페 — 공개 API로 시도 + 자가진단
많은 지역 대회가 **네이버 개방카페**에만 상세 요강을 올린다(정읍사=cafe.naver.com/kjeongup).
네이버 웹검색·카페 웹페이지는 클라우드에서 차단되지만, **카페 공개 API는 다를 수 있으니 시도하고
결과를 자가진단**한다(개방카페 한정, 로그인 불필요):
- 글 목록: `https://apis.naver.com/cafe-web/cafe2/ArticleListV2dot1.json?search.clubid=<clubid>&search.queryType=lastArticle&search.page=1&search.perPage=30`
- 본문:   `https://apis.naver.com/cafe-web/cafe-articleapi/v2.1/cafes/<clubid>/articles/<articleId>?query=&useCafeId=true&requestFrom=A`  (헤더 `Referer: https://m.cafe.naver.com/`)
- clubid는 카페 홈 HTML/게이트에서 확인. (실측 성공(가정용 IP): kjeongup=clubid 30506445, 제36회 요강 글 no=123~126, 접수마감 8.17 확보)
- ⚠ **자가진단 필수**: 위 API가 클라우드 IP에서 `http=200` + 정상 JSON을 주는지 **먼저 확인**한다.
  차단(403·빈 응답·비JSON)되면 카페는 이번 실행에서 **불가**로 로그하고, 그 대회를 **심층 재감사 대상으로 플래그**한다.

### (3) 인스타그램 — 클라우드 불가(로그인 벽) → 심층 재감사로 넘김
흥길마당(@heunggil_madang) 등 인스타 큐레이터에만 뜨는 공고가 있으나, **인스타는 로그인 벽이라
헤드리스 curl로 캡션을 못 읽는다**(실측: 프로필·개별 게시물 모두 로그인 벽, og:description 비어 title만 "Instagram").
카드뉴스 이미지라 OCR도 필요. → 클라우드 루틴은 인스타를 **시도하지 않는다**(시간 낭비).
기존 항목 `source`에 instagram이 있거나 인스타에만 있는 정황이면 **심층 재감사 대상으로 플래그**만.

### (4) 심층 재감사(B-1) — 클라우드 사각지대 메우기
네이버·인스타·로그인 필요 소스는 **가정용 IP + 로그인 브라우저를 쓰는 대화형 세션**(관리자가 Claude와
함께 실행)에서 주기적으로 **전수 재감사**해 메운다. **작업목록 = `tools/monitor/pending_review.json`**
(클라우드 루틴이 로그인 벽 등으로 완성 못 해 등록해 둔 것) + 위 (2)(3) 플래그 + `confidence: partial`
+ `applyStart`/`applyEnd` 빈 항목. 그 세션에서 공홈/개방카페/인스타를 직접 확인해 보강하고,
**완성된 항목은 pending_review.json에서 제거**한다. **목표: 배포 전 풀 목록 완성.**
(클라우드 루틴 = 상시 감시, 심층 재감사 = 사각지대 완성.)

## ★ 신뢰성 검증 게이트 (반영 전 필수 — 하나라도 걸리면 그 항목 스킵)

각 후보 사실(날짜·회차·장소 등)은 아래를 **모두** 통과해야만 changes.json에 넣는다. 사용자가 오류를
못 잡으므로, "확실치 않으면 넣지 않는다"가 기본값이다.

1. **소스 확정 (3소스 신뢰).** 날짜·회차·장소·접수는 국악신문·국악타임즈·콘테스트코리아 중
   **한 곳 이상에서 확인되면 반영**한다. 공홈(지자체·문화재단)이 열리면 교차확인해 더 정확히 —
   하지만 **공홈이 없거나 503 등으로 안 열려도 3소스 정보로 반영한다**(공홈은 필수가 아님).
   소스 어디에도 정보가 없어 확인 자체가 안 되는 것만 스킵.
2. **요일 정합성 (연도 오류 잡는 결정타).** 공고가 요일을 명시하면(예: "7. 11.(토)"), 그 날짜의 **실제
   요일을 계산해 일치하는지** 확인한다. 불일치 = 연도/날짜 오류 → 스킵·재확인.
   확인법: `python3 -c "import datetime;print(datetime.date(2026,7,11).strftime('%a'))"` (Sat=토).
   (실측 예: 2026-07-11=토, 2025-07-11=금 → 공고가 "(토)"면 2026이 맞다.)
3. **회차↔연도 정합성.** 연 1회 대회면 제N회=YYYY, 제(N+1)회=YYYY+1. 새 회차는 데이터셋 최신 회차의
   **+1**이어야 하고 연도가 주기와 맞아야 한다. 모순(예: 데이터 제25회=2026인데 "제26회=2026")이면
   플래그·스킵. **회차 건너뜀·연도 역행**은 의심 신호.
4. **공고 시점 상식.** 공고 발행일이 개최일보다 앞서고(보통 1~3개월 전), 개최일이 오늘 기준 과도한
   과거/미래가 아닌지. (발행일은 게시글에서 클로드가 읽어 확인.)
5. **단일 소스도 신뢰.** 3소스(국악신문·국악타임즈·콘테스트코리아) 중 한 곳에서만 확인돼도 반영한다
   (교차확인 필수 아님). 공홈이 함께 확인되면 더 좋다.
   - ★ **단, 공지는 종종 바뀐다** — 개최일·장소 변경, 접수 연기, 요강 수정 등. 한 번 기록했다고
     고정으로 보지 말 것. **기존 항목도 매일 재확인**해 변경이 있으면 갱신하고, **항상 최신 공고
     상태**를 사실로 삼는다(소스끼리 과거·현재가 다르면 최신이 우선).
6. **확신 게이트.** 위 중 하나라도 불확실 → **넣지 않는다.** (오탐을 넣는 비용 ≫ 하루 늦게 잡는 비용)

> 위 검증은 클로드가 **읽고 추론해서** 수행한다(요일 계산만 파이썬 한 줄 사용). 정규식으로 페이지에서
> 숫자를 긁어 그대로 쓰는 방식은 금지 — 그게 바로 회차·연도 오탐의 원인이다.

## 실행 모드 = 매일 딥서치 (요일 분기 없음)

**요일 구분을 두지 않는다. 매일 아래 딥서치를 그대로 수행한다.** (구 "평일 적시 스캔(얕고 빠름) /
일요일 전수 점검" 이원 구조는 폐기 — 적시 스캔이 골격만 만들고 접수시작 등 필드를 비운 채 두어
"모름 → 며칠 뒤 채움"의 갱신 노이즈와 phase 오판을 유발했다. 이제 첫 발견부터 깊게 채운다.)

매 실행마다:

1. **3소스 깊게 열거.** 국악신문·국악타임즈·콘테스트코리아 각각에서 **섹션/카테고리 목록 + 키워드
   검색을 둘 다**(위 "목록+검색 병행" 필수) 수행하되, **최근만이 아니라 여러 페이지 깊게** 훑는다
   (과거 목록·검색·카테고리 폭넓게 — 소스별 병렬 서브에이전트 가능). 시간이 더 걸려도 **빠짐없이.**
2. **신규 전수 추림.** 열거한 대회를 정규화해 `all_keys`에 **없는 것**을 전부 추려 `new` 후보로,
   기존 대회의 **회차전환·일정변경**도 함께 재확인해 `update` 후보로 삼는다.
3. **★ 완전 추출 (골격 금지).** 각 후보는 아래 "루틴 지시" 4단계대로 **본문+첨부 요강(.hwp/pdf)+공홈**
   까지 읽어 접수시작·마감·개최일·장소·부문을 **채워서** 넣는다. 접수시작을 못 구하면 반드시
   `confidence: partial`로 표기한다(빈 채로 완성인 척 금지 — 아래 "필드 완전성 규칙" 참조).
4. **★ 보강 (풀 목록 완성) — 매일 수행.** 기존 항목 중 **`confidence: partial` 이거나
   `applyStart`/`applyEnd` 중 하나라도 빈** 항목을 추려, 위 "공홈·확장 소스 검색"대로
   **공홈/개방카페 공개 API + 첨부 요강**으로 접수시작·마감·부문·참가비를 보강한다.
   개방카페 API가 클라우드에서 막히면(자가진단) 그 대회를 **심층 재감사 대상으로 로그**한다.
5. 나머지 절차(검증 게이트 → `safe_merge.py` → `git add competitions.json` → push)는 동일.

> 트레이드오프: 매일 딥서치는 실행시간·토큰이 늘지만, "적시 + 빠짐없이 + 첫날부터 완전"을 한 번에
> 보장한다. 완전성·정확성이 비용보다 우선이다(잘못/빈 데이터가 실사용자 앱에 바로 노출되므로).

### ★ 필드 완전성 규칙 — "한 방에 완성" (골격 커밋 금지)

**공고는 처음부터 완전하게 게시된다** — 주최측이 접수기간·장소·부문을 빠뜨린 반쪽 공고를 내고
나중에 채우는 일은 없다. 따라서 **데이터에 골격(partial)이 생기면 그건 소스가 부족한 게 아니라
우리가 못 뽑은 것**이다. 같은 공고를 다음날 다시 봐도 같은 결과이므로 **"다음날 backfill로 채워진다"에
기대지 않는다** — 첫 발견에 한 방에 완성한다. (찔끔찔끔 채워지거나 날짜가 조금씩 바뀌는 것은
추출 부실의 증상이며, 앱에서 가짜 '수정' 알림·불안정을 유발한다.)

**실측(2026-07): 요강 필드가 실제로 어디 있나 —**
- **.hwp 첨부는 대개 참가신청서 양식**이라 접수기간·장소가 **없다**(요강인 경우만 있음).
- **기사 본문 텍스트**는 흔히 **접수마감만** 싣는다(접수시작 누락 잦음).
- **포스터 이미지**에 **요강 전체(접수시작·마감·장소·부문·참가비)가 담긴 경우가 가장 많다.**

**추출 = 세 소스(hwp 첨부 + 기사 본문 + 포스터/요강 이미지) 종합·교차확인 — 모든 필드에 적용:**
어느 한 소스에서 값을 찾아도 **멈추지 말고 셋 다 읽어**, **날짜·장소·부문·부별·참가자격·경연시간·참가비·
연락처·접수방법 등 모든 필드를 세 소스로 대조해 확정**한다. **한 소스만 보고 확정하지 않는다.**

- **일치하면 확정. 불일치하면 플래그 + 요강 원문(포스터·hwp요강) 우선**(기사 본문 요약보다 권위 높음),
  날짜 게이트(요일·순서·회차↔연도)로 검증. (실측: 서천 — 본문엔 접수마감만, **포스터 요강에 접수시작 7.1**
  → 포스터로 확정. hwp는 참가신청서 양식이라 없었음. 본문만 봤으면 놓쳤을 필드다.)
- **각 소스 취급법(셋 다 시도):**
  - **.hwp/pdf 첨부**: 그누보드 `download.php`는 세션 없으면 `잘못된 접근`으로 막힌다 → **기사 URL을
    쿠키자로 먼저 방문(PHPSESSID)** 후 그 쿠키+Referer로 받는다
    (`curl -c cj "<기사URL>" -o /dev/null && curl -b cj -e "<기사URL>" "<download.php?..&no=N>" -o f.hwp`).
    파싱: `.hwp`(OLE) → `olefile`로 `PrvText` UTF-16LE(도구 없이 py에서 됨, 실측), 정밀히는 `hwp5txt`/
    BodyText zlib. `.hwpx`=`unzip`→`Contents/section*.xml`. `.pdf`=`pdftotext`. **⚠ hwp는 대개 참가신청서
    양식이라 요강이 아닐 수 있다 — 그래도 확인은 한다.**
  - **기사 본문 텍스트**: 흔히 접수마감만 싣는다(다른 필드 누락 잦음) → **본문만 믿지 말 것.**
  - **포스터/요강 이미지**: 게시글 본문의 `/data/editor/…` 또는 `/data/file/news/…` 이미지(썸네일 제외)를
    받아 **비전으로 판독**. 요강 전체(접수기간·장소·부문·자격·경연시간·참가비)가 담긴 경우가 가장 많다
    → **반드시 열어 읽는다.** (포스터가 여러 장이면 상세 요강 페이지까지 다 본다.)
- ⚠ 본문·OCR·hwp에서 얻은 **날짜·회차는 요일 정합성·회차↔연도 게이트로 교차검증**(연도 오타·오독 차단).
  소스 자체가 요일을 틀리게 쓴 경우(실측: 서천 요강 "7.1(화)"인데 실제 수)도 잡아 **실제 요일로 바로잡는다.**

**필수 필드 = 접수시작·접수마감·개최일·장소·부문.** 세 소스를 다 종합해도 못 채운 필드가 있으면:
- 원인은 사실상 **로그인 벽 소스뿐**(네이버 카페·인스타에만 요강 → 클라우드 IP 접근 불가). 이런 경우만
  **`confidence: partial`** 로 남기고 **`pending_review.json` 대기목록**(officialName·빠진 필드·sourceUrl)에
  기록해 **관리자 심층 재감사 세션**으로 넘긴다. (partial은 "다음날 자동"이 아니라 사람 손이 필요한 큐다.)
- 그 외(도구·세션 문제로 못 읽은 것)는 **partial로 얼버무리지 말고 세 소스로 끝까지 뽑는다.**
- **⛔ 추측 금지 — 모든 필드에 적용.** 어느 필드든 세 소스에 없다고 **지어내지 않는다.** 특히 접수시작을
  **"공고일/기사 게재일로 추정"하지 말 것**(실책 사례). 확정본만 넣고, 없으면 비우고 partial — 나중에
  "조금씩 수정"으로 가짜 '수정' 알림을 만들지 않는다.

## 루틴 지시 (매일 실행)

1. **준비**: 이 저장소(concours-data)에서 실행된다. 스크립트는 tools/monitor/ 에 있다.
2. **타깃 생성**:
   `python3 tools/monitor/targets.py --file competitions.json > targets.json`
   → `targets[]`(곧 개최 예정이라 새 회차가 뜰 만한 대회) + `all_keys`(전체 정규화 키, 신규 판별용).
3. **스캔**: 3소스(국악신문·국악타임즈·콘테스트코리아) 각각에서 **섹션 목록 + 키워드 검색을 둘 다**
   수행해(위 "목록+검색 병행" 필수) 아래를 찾는다.
   - **(a) 회차 전환**: `targets[]`의 각 대회에 대해, 마지막으로 알려진 `lastRound`보다 **새 회차**가
     공고됐는가? (예: lastRound=51 → 제52회 공고 발견) → `update` 후보.
   - **(b) 일정 변경**: 기존 대회의 접수마감·대회일이 바뀌었는가? → `update` 후보.
   - **(c) 신규 대회**: 정규화 이름이 `all_keys`에 **없는** 대회가 공고됐는가? → `new` 후보.
   - 정규화 규칙: 회차·연도·괄호·공백 제거(`targets.py`의 base와 동일). `update`의 `match_base`에는
     반드시 `targets[].base` 값을 그대로 쓴다(직접 만들지 말 것).
4. **사실 확정 (한 방에 완성 — 위 "필드 완전성 규칙" 준수)**: 각 후보의 사실은 **기사 본문 + 첨부
   요강(.hwp/pdf) + 포스터 + 공홈**을 **모두** 열어 클로드가 풀 추론으로 판독(이미지면 비전 OCR)해
   **첫 실행에 완성도 있게** 채운다. 기사 본문은 접수마감만 싣는 경우가 많으니 **첨부·공홈을 반드시
   함께** 읽는다. **모든 필드를 세 소스(hwp·본문·포스터) 종합·교차확인으로 확정**한다(한 소스만 보고
   확정 금지 — 상세는 "필드 완전성 규칙" 참조). 불일치는 요강 원문(포스터·hwp요강) 우선 + 게이트 검증.
   **특히 접수시작은 본문·hwp엔 없고 포스터에만 있는 경우가 많으니, 반드시 포스터를 OCR해 확인한다**:
   날짜(`competitionDate`), 접수기간(`applyStart`/`applyEnd`), 장소(`venue`), 부문(`genres`), 부별(`levels`),
   지역(`region`), 주최(`host`), 회차(`round`), 월(`month`=YYYY-MM), 공고 링크(`sourceUrl`).
   - ★ 각 항목은 위 **신뢰성 검증 게이트를 통과해야만** 채택 — 3소스 신뢰(게이트 1·5)이되, 날짜·회차의
     **내부 정합성**(요일·회차↔연도·공고시점)은 반드시 확인. 정합성 모순이면 스킵. (OCR 값은 필수 교차검증.)
   - **확인 안 된 필드는 비운다(추측 금지).** 정규식으로 긁은 값 그대로 쓰지 않는다.
   - **필수 필드(접수시작·마감·개최일·장소·부문) 중 하나라도 못 채우면 `confidence: partial`** + 아래
     `pending_review.json`에 기록. 골격(마감만·나머지 빈)을 완성인 척 커밋하지 않는다. **단, partial은
     "다음날 자동 보강"이 아니라 관리자 심층세션이 처리하는 큐다** — 도구·세션 문제로 못 읽은 것은
     partial로 얼버무리지 말고 위 fallthrough로 끝까지 뽑는다(공고는 애초에 완전하므로 못 뽑음=우리 탓).
   - `sourceUrl`은 확인한 원문 링크(3소스 게시글 또는 공홈). 포스터는 공홈 원본만 —
     이 루틴에선 `noticeImages`를 비워 둔다(포스터 수집은 별도 트랙).
5. **변경 작성**: 위 후보들을 `changes.json`으로 만든다(형식은 `safe_merge.py` 상단 주석 참조).
6. **안전 반영**:
   `python3 tools/monitor/safe_merge.py --file competitions.json --changes changes.json`
   → 요약과 `COMMIT_MSG:` 한 줄이 출력된다. (변경 0이면 여기서 종료 — 커밋하지 않음)
7. **대기목록 갱신**: 완성 못 한(로그인 벽 등) partial 항목을 `tools/monitor/pending_review.json`에
   기록한다 — `[{officialName, missing:[빠진 필드], sourceUrl, reason}]`. (관리자 심층세션이 이걸 보고 메움.)
   더 채워 넣어 완성된 항목은 목록에서 제거한다.
8. **커밋 & push** (concours-data에서):
   - `git add competitions.json tools/monitor/pending_review.json` ← **이 둘만.** (`git add -A`/`git add .` 금지)
   - `git status`로 `images/` 삭제(`D images/...`)나 의도치 않은 변경이 없는지 확인. 있으면 **중단**.
   - `git commit -m "<COMMIT_MSG 내용>"` → `git push origin main`.
   - `.bak.monitor*` 백업 파일은 커밋하지 않는다(스테이징에서 제외).
9. **보고**: 그날 무엇을 추가/갱신했는지(safe_merge 요약) + 대기목록(pending_review) 건수를 로그로 남긴다.

## 실패·불확실 처리
- **공고는 완전하게 게시되므로 "다음날 다시 시도하면 채워진다"에 기대지 않는다.** 못 뽑았으면 오늘
  fallthrough(hwp→본문→포스터 OCR)를 끝까지 써서 뽑는다. 그래도 안 되는 유일한 경우는 로그인 벽 소스.
- **로그인 벽으로 완성 불가한 것만** `confidence: partial` + `pending_review.json` 등록 → 관리자 심층세션.
- 사실 자체가 소스 어디에도 없어 확인 불가한 신규는 보수적으로 **보류**(넣지 않음).
